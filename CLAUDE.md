# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server (Turbopack) at localhost:3000
- `npm run build` — production build
- `npm run typecheck` — `tsc --noEmit`
- `npm run lint` — ESLint (flat config, includes the React Compiler / `react-hooks` rule set — notably `react-hooks/set-state-in-effect`, which disallows synchronous `setState` calls inside `useEffect` bodies; prefer deriving state or `useSyncExternalStore` for browser-API subscriptions instead)
- No test suite exists yet.

Copy `.env.example` to `.env.local` and fill in `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` (signups), `ADMIN_PASSWORD` (the `/admin` page), and `NEXT_PUBLIC_GA_MEASUREMENT_ID` (analytics) to have those work locally — all no-op or fail gracefully when unset rather than crashing.

## Architecture

Next.js 16 App Router, TypeScript, Tailwind CSS v4 (CSS-first config — no `tailwind.config.ts`; all design tokens live in `app/globals.css` under `@theme inline`). Single route (`/`) composed of section components in `components/sections/` (`Header` → `Hero` → `HowItWorks` → `Activities` → `SignupSection` → `Faq` → `Footer`), assembled in `app/page.tsx`. `SignupSection` is a dark card holding the closing pitch copy, the signup form, and the store buttons — it used to be a separate `ClosingCta` section plus a form embedded in `Footer` with a near-duplicate heading, so the two were merged; `Faq` was then moved to sit after `SignupSection` rather than before it, so the FAQ reads as "one more thing before you decide" rather than a detour before the form. `Footer` itself is back to being just the bottom bar (lockup, socials, anchor links, © line) — it doesn't hold the form despite the name similarity to earlier iterations. No other routes/pages exist — do not add multi-page navigation, per the PRD. The sticky `Header` has in-page anchor links only (How it works / Activities / FAQs, shown at ≥760px), which the v2 design added; they jump within the single page. `HowItWorks` was re-imported from `KOODAL Landing v3.dc.html` (UI only, per user instruction — the rest of the page stayed on the v2 design; v3's OMR wording and other section changes were not carried over).

The visual design (palette, fonts, copy, layout, animation timing) was imported from a Claude Design project ("Landing page design specifications", currently `KOODAL Landing v2.dc.html` + `Signup Form.dc.html` + `Koodal Lockup.dc.html`) via the `DesignSync` tool's read methods — not built from scratch. The design's `image-slot.js` and `support.js` are the design tool's own runtime and aren't ported. Its empty photo slots in How it works are rendered as flat "seats filling up" illustrations (`components/ui/AnimatedSteps.tsx`) instead, keeping the flat-illustration identity until real photos exist. Wherever the design text says "OMR", the site uses "Chennai" (a standing product decision). Palette: cream background `#faf7ef`, ink `#15191a`, lime primary `#d4e031`, coral accent `#ff6a4d`, teal `#0f7f76`. Fonts: Bricolage Grotesque (headings) + DM Sans (body). If the design changes, re-fetch it the same way rather than hand-guessing new values — the current tokens/copy should stay traceable to that source.

Key pieces:
- **`components/ui/KoodalLockup.tsx`** — the wordmark: the "Converge" mark (four wedges arriving from four directions) + "KOODAL" with the double-O drawn as two overlapping rings. Ported from the design's "Koodal Lockup" component (mark variant "a", the recommended one — variants "b"/"c" were explored but never used and aren't implemented). `app/icon.tsx` and `app/opengraph-image.tsx` reuse the same mark paths standalone (Satori/`next/og` can't render this component directly, so the SVG is duplicated inline there — keep both in sync if the mark changes).
- **`context/SignupProvider.tsx`** — the single source of truth for the signup form: the array of picked activities (multi-select — see below), the `intent` pick ("I have a plan and need people" / "I want to join a plan" / "Both"), the `name`/`whatsapp`/`areaPincode`/`email`/`consent` field values, and submitted/submitting state. `submit()` returns `{ok, error?}` rather than storing an error centrally — `CtaForm` keeps its own local error string. `FORM_NAME_INPUT_ID` lives here too, used for scroll-to-focus targeting (the Name field is the form's first field). There is no signup counter — the design dropped the numeric social proof in favor of a static "Currently onboarding the first group" line.
- **Activities are multi-select**, identified directly by their literal label string (`ActivityLabel` in `lib/types.ts`), not a slug/id — matching the source design, which operates on label strings as the canonical key throughout. `lib/activities.ts` defines a single flat structure, `ACTIVITY_GROUPS` (Hang / Explore / Go Out / Play, 14 activities total), rendered as colored pills via `components/ui/ActivityPill.tsx` — no separate "featured" row or photo treatment (deliberately dropped to keep the page's flat-illustration identity rather than drifting toward stock photography). Group colors are data-driven so pills use inline styles, not Tailwind classes, for their selected-state fill.
- **`components/ui/PlanPreviewCard.tsx`** — the hero's illustrative card auto-rotates through `DEMO_PLANS` (`lib/activities.ts`) every 3.2s via `setInterval`; the rotation is skipped entirely (not just sped up) under `prefers-reduced-motion`, showing the first demo statically instead.
- **The signup form lives only in `components/sections/SignupSection.tsx`**, inside a dark rounded card that also carries the closing pitch copy ("Drop your details. We'll bring the rest.", "You meet through the plan, not a random DM.") and the App Store / Google Play `StoreButtons`. Every "Get Early Access" button elsewhere on the page (nav, Hero, How it works, Activities, sticky mobile bar, store buttons) calls `scrollToSignupForm()` (`lib/scrollToForm.ts`) via `components/ui/CountMeInButton.tsx`, which scrolls down and focuses the Name field rather than embedding a duplicate form.
- **`components/ui/CtaForm.tsx`** — the form: intent picker, then a two-column grid of Name / WhatsApp number / Area-Pincode / Email (optional) fields (stacks to one column below `sm:`), then a required consent checkbox, then submit ("Get Early Access"). It's styled only for its one home — `SignupSection`'s dark card — not theme-switchable. Field focus styling is pure CSS (`:focus-within` on a `group` wrapper) rather than per-field JS state. `lib/validateSignup.ts` (`validateSignupFields`) is the shared client + server validator — loose on format, strict on presence, and requires `consent` to be `true` before it will submit.
- **The consent checkbox exists for India's DPDP Act**, which requires stating why data is being collected before collecting it. Its copy ("I agree to be contacted about KOODAL plans on WhatsApp or email...") is the compliance-relevant text — if the purpose of data collection changes, update this line, not just the backend.
- **`app/api/signup/route.ts`** — validates (via `validateSignupFields`) and inserts each submission into a Supabase `signups` table via `lib/supabase.ts`'s `getSupabaseAdmin()`. This replaced an earlier Google Apps Script webhook → Google Sheet flow entirely (no dual-write) — Supabase's own Table Editor is now the "open a spreadsheet and look at signups" tool, alongside the `/admin` page below. `activities` is inserted as a native Postgres `text[]` (not a joined string); `areaPincode` → `area_pincode` to match the snake_case column. Invalid/unknown activity strings are silently filtered out (not rejected) rather than erroring the whole request. `getSupabaseAdmin()` returns `null` when `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are unset, and the route fails gracefully (502, friendly message) rather than crashing — same pattern the old webhook check used. **The service role key is used deliberately** (bypasses Row Level Security) rather than the anon key + an insert policy, so the `signups` table has RLS enabled with zero policies — nothing but server-side code holding that key can read or write it. The Supabase project/table is a manual setup step, not code in this repo:
  ```sql
  create table public.signups (
    id uuid primary key default gen_random_uuid(),
    created_at timestamptz not null default now(),
    name text not null,
    whatsapp text not null,
    area_pincode text not null,
    email text,
    activities text[] not null default '{}',
    intent text not null,
    consent boolean not null
  );
  alter table public.signups enable row level security;
  ```
- **`app/admin/page.tsx` + `components/admin/AdminSubmissions.tsx` + `app/api/admin/submissions/route.ts`** — a private, unlinked page for the founder to review signups without opening Supabase directly: a password gate, then a plain table + "Download CSV" button. This is the "raw signup export" the PRD's out-of-scope list explicitly still allows (see below) — deliberately kept to just that, no filtering/editing/analytics. The password check is **duplicated in two places on purpose**: the page component gates the UI client-side (the requested UX), but `app/api/admin/submissions/route.ts` independently re-checks the same password server-side (`ADMIN_PASSWORD` env var, `crypto.timingSafeEqual`) before querying Supabase — without that second check, the data endpoint could be called directly, bypassing the client-side gate entirely. `ADMIN_PASSWORD` must never be `NEXT_PUBLIC_`. The page has `robots: { index: false, follow: false }` and isn't linked from anywhere public. A correct password is cached in that tab's `sessionStorage` (re-verified against the server on each load) so a refresh doesn't re-prompt, but a new tab does.
- **`hooks/useInView.ts` / `hooks/useReducedMotion.ts`** — scroll-reveal animation is hand-rolled via `IntersectionObserver`, no animation library, to protect the PRD's <2s/4G load budget. Reduced-motion support short-circuits `useInView` to always-visible rather than branching per-component.
- **`lib/analytics.ts`** — thin wrapper around `@next/third-parties/google`'s `sendGAEvent`; centralizes the custom GA4 events (`scroll_depth`, `cta_click`, `signup_success`).

## What KOODAL is

KOODAL (Tamil for "gather"/"bring together") is a validation landing page for a product idea, not the product itself. The idea: help Chennai's pickleball/padel, badminton, board-game and quiz-night crowd fill missing headcounts in group plans. The page's only job is to convert a targeted visitor into a signup (name, WhatsApp number, area/pincode, and optional email) as a proxy for real demand, before any matching app is built.

The full spec lives in `Koodal Landing Page — PRD.md`. Read it before implementing — the notes below are the requirements that most constrain implementation decisions, not a replacement for the PRD.

## Product constraints that drive implementation

- **Single page, single scroll, single CTA.** No multi-page routing (the header's in-page anchor links are the only navigation), no login/accounts. Every section exists to move the visitor toward one form — the extra "Get Early Access" buttons all lead to the same `SignupSection` form.
- **The CTA form's fields**: Name, WhatsApp number, Area/Pincode, Email (optional), plus the picked activities carried over from the Activities section, an "intent" pick (has a plan / wants to join / both), and a required consent checkbox. Note: the original PRD asked for exactly one text input (WhatsApp number or Instagram handle), on the grounds that every extra field lowers conversion — this was deliberately overridden to collect the fields above plus explicit consent, per India's DPDP Act requirement to state a purpose before collecting personal data. Don't "simplify" the form back to one field without re-confirming the legal requirement is still satisfied another way.
- **Mobile-first, and mobile-only in practice.** Design for a 375–430px viewport first; almost all traffic is Instagram/Meta ad clicks and community-page links opened on a phone. No feature should depend on desktop-only interaction.
- **Performance budget: under 2 seconds to load on typical 4G.** Keep JS/CSS-driven animation; avoid heavy video or large Lottie files that would blow this budget.
- **Accessibility floor**: sufficient color contrast, 16px minimum body text, and the page must be fully functional with `prefers-reduced-motion` set (fall back to instant state changes, no motion).
- **Animation must never block interaction** — the CTA has to be clickable immediately even mid-animation. Section reveals fade/slide on scroll; "How it works" steps animate in sequence, not simultaneously; activity cards get a hover/tap scale/lift; the CTA button gets a scale + color-shift micro-interaction; form fields get focus-state animation; successful submit replaces the form with a short confirmation.
- **Visual direction**: warm/energetic palette (teal + coral/orange + soft yellow) matching existing offline poster material, flat-illustration style, bold sans-serif type, rounded shapes, generous whitespace — aimed at a young urban Indian (Gen-Z/20s-30s) audience.
- **Page sections, in order** (per the imported design, with `Faq` since repositioned): sticky Header (wordmark + in-page anchor links + "Get Early Access") → Hero (tagline + subhead + "Get Early Access" button (scrolls to the signup form) + avatar strip + rotating illustrative plan-card) → How it works (dark card, per the v3 design: a sticky left info panel with a live "0X / 04" step counter + "Get Early Access", beside a 4-step connecting-line timeline whose fill and dot/title highlighting track scroll position — see `components/sections/HowItWorks.tsx` — steps per the PRD's mechanic: Post your plan → People nearby join & confirm → Your group forms → The plan happens) → Activities (grouped pill picker across 4 groups, 14 activities total, multi-select, see `lib/activities.ts` — tapping tags interest, + "Get Early Access") → SignupSection: a dark card (the "Now starting in Chennai" credibility line + closing pitch copy + the signup form itself, see `components/ui/CtaForm.tsx`, + "coming soon" App Store / Google Play buttons from `components/ui/StoreButtons.tsx` — placeholders with no real store links, since no app exists yet and official store badge artwork is only allowed for live apps) → FAQs (accordion, first item open — deliberately placed after the form rather than before it, as one more reassurance before the page ends rather than a detour on the way to signing up) → Footer (Instagram + WhatsApp community icon links, anchor links, © line — no form here).
- **Backend needs are minimal by design**: submissions (name, WhatsApp number, area/pincode, optional email, activity tags, consent, timestamp) must persist somewhere the founder can review — no full app backend at this stage. That "somewhere" is a Supabase table today, reviewable either in Supabase's Table Editor or via the password-gated `/admin` page. Analytics must at minimum capture page views, scroll depth, CTA clicks, and conversion rate, since the whole point of the page is to measure conversion against a 10–20% target (below 3–5% means the pitch/targeting needs rework).
- **Hosting**: needs a single public shareable link that behaves identically whether opened from WhatsApp, an Instagram bio link, or a paid ad — no environment-specific behavior.

## Explicitly out of scope

Do not build: real plan-posting/matching functionality, account creation or login, payment or venue-booking integration, a multi-page site, or an admin dashboard beyond a raw signup export. `/admin` (see above) is that allowed raw-export exception — a table + CSV download behind a single shared password, not a login system — and should stay that minimal; don't grow it into filtering, editing, analytics, or multi-user auth. These belong to a later manual-concierge MVP or the real app, not this landing page.
